# Доставка заявок в CRM Хаят

Интеграция принимает новые розничные заказы сайта/API v1/API v2, оптовые заявки и консультации сайта/API v2. Для каждого принятого документа в той же транзакции создаётся неизменяемый снимок `CrmOutbox`. Сеть вызывается после фиксации документа. Ошибка CRM, записи подтверждения, кэша или сохранения дополнительного адреса не отменяет принятый заказ.

## Подготовка

На новой установке сначала создать схему из `prisma/schema.prisma` обычным процессом установки. Для существующей базы подготовлен только добавляющий объекты SQL `prisma/changes/20261112_crm_outbox.sql`; выполнение на рабочей базе требует отдельного согласования. После применения схемы выполнить `pnpm exec prisma generate`, затем проверки и сборку. Старые документы не импортируются автоматически.

Серверные переменные:

| Переменная | Назначение |
|---|---|
| `CRM_PROVIDER=hayat` | Направлять новые записи в CRM Хаят |
| `HAYAT_CRM_URL` | HTTPS origin CRM, например `https://crm.example.ru`; без пути, query и пароля |
| `HAYAT_CRM_TOKEN` | Отдельный токен источника `biohayat`, не менее 32 символов |
| `CRM_DRAIN_TOKEN` | Независимый токен запуска очереди, не менее 32 символов |

Токены задаются в окружении сервера и не попадают в настройки публичного API. На стороне CRM должны быть явно настроены токен, существующая воронка, открытая стадия и активный ответственный. При отсутствии URL/токена заявка сохраняется и получает видимую повторяемую ошибку. Другой получатель автоматически не выбирается.

Unset `CRM_PROVIDER` или `bitrix` сохраняет прежнее поведение новых записей. Неизвестное значение считается ошибкой конфигурации. Выбор получателя фиксируется в момент создания: смена переменной не перенаправляет ранее принятые заявки.

## Повторы и наблюдение

Планировщик должен запускать каждые 1–5 минут:

```sh
curl --fail --silent --show-error --request POST \
  --header "Authorization: Bearer $CRM_DRAIN_TOKEN" \
  https://shop.example.ru/api/crm/drain
```

Храните токен в защищённом окружении задания; не помещайте его в URL или журналы. Каждый запуск ограничен десятью заданиями и бюджетом времени. Задание получает аренду на 90 секунд; запись результата проверяет уникальный токен аренды. При остановке процесса следующая попытка заберёт истёкшую аренду. Таймаут одной отправки — 8 секунд. Сетевые ошибки, 408/429/5xx повторяются с увеличением интервала от 30 секунд до часа; остальные ошибки сохраняются для проверки оператором. Ответ 200/201 принимается только с совпадающими видом/ID события и корректным ID сделки.

Раздел `/admin/crm-deliveries` показывает все недоставленные розничные, оптовые и консультационные события, ошибки, число попыток и действие повтора. Карточка розничного заказа показывает доставку отдельно от старых ID Битрикс24. Успешная повторная доставка использует первоначальный снимок; документ в CRM создаётся ровно один раз по его внешнему ключу. Снимки и подтверждения сохраняются независимо от последующего удаления исходной заявки; правила дальнейшего хранения требуют отдельного решения владельца данных.

Публичный контракт заказа не меняется. У старых клиентов без ключа запроса повторная отправка самой формы может создать второй исходный заказ; гарантия идемпотентности касается доставки одной сохранённой записи. V2 продолжает использовать существующие `requestKey`/`requestHash`.

## Совместимость и откат

Старые ID/настройки Битрикс24 остаются доступны. Вебхуки Битрикс24 могут менять только заказы `crmProvider=LEGACY`, включая поиск по номеру. Новые заказы Хаят не принимают статусы от старого токена. Обратная синхронизация статусов, товаров и остатков с CRM в эту поставку не входит.

Безопасный откат настройки — вернуть provider для **новых** записей; существующие задания Хаят продолжать разбирать текущим обработчиком. Откат к коду до этой интеграции временно остановит очередь и вернёт старые правила вебхука, поэтому перед таким откатом нужно остановить обработку старых вебхуков/входящих заявок и согласовать операционный план. Добавленные таблицы, поля, снимки и подтверждения не удалять. Нельзя переводить записи очереди в Битрикс24 для обхода ошибки CRM.

Для изолированных тестов HTTP разрешён только на loopback при `HAYAT_CRM_ALLOW_LOOPBACK=true` и `NODE_ENV` не `production`; производственная конфигурация использует HTTPS. Перенаправления не выполняются. Линтер, типы, DB-тесты и сквозная проверка с CRM обязательны до выпуска.

Регрессии: `CRM_TEST_ALLOW=1 TSX_TSCONFIG_PATH=scripts/tsconfig.crm-tests.json pnpm exec tsx scripts/test-crm-outbox.ts`. Скрипт принимает только специально созданную базу `hayat_shop_crm_test` на `hayat-commerce-test-postgres:5432`, данные подключения передаются через защищённое окружение. Выполняет настоящие транзакции и все шесть серверных точек входа, подменяя только внешние HTTP-запросы. Проверяет ошибки после commit, откат вставки outbox, аренды/параллельные повторы и работу при PostgreSQL timezone Europe/Moscow. Тестовый tsconfig разрешает маркер `server-only` в штатную серверную реализацию Next, обычный tsconfig приложения не меняется.
