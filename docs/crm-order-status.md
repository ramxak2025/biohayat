# Shop authority for CRM order status

The shop owns retail/wholesale status and retail accounting. CRM stages submit commands; they never edit shop tables or infer accounting from stage labels.

`GET /api/crm/order-status?kind=retail_order|wholesale_order&orderId=…&dealId=…` returns `{schemaVersion:1,kind,orderId,dealId,status,revision}`. `POST` accepts those identifiers plus `{schemaVersion:1,eventId:<uuid>,expectedRevision:<integer>,status:<existing enum>}`. Both require the dedicated `HAYAT_CRM_STATUS_TOKEN` Bearer credential. It must differ from source ingress, drain and session secrets. A matching persisted HAYAT ingress receipt links kind/order/deal; source tokens and customer sessions grant no reverse access.

The command takes an event lock and an order row lock. Same event/body replays the immutable receipt; changed reuse returns `409 event_conflict`. A stale revision or a terminal reopen returns a durable `409` receipt with the canonical state. Success is `200` with `applied:true`, code `applied|unchanged`. Retail `CANCELLED/DELIVERED` and wholesale `CANCELLED/DONE` cannot be reopened through CRM. Existing deliberate shop-admin workflows retain their behavior. Retail reservations/bonuses change in the same transaction and only existing recorded reservations can be restored. Wholesale adds no inventory or bonus behavior.

Apply `prisma/changes/20261112_crm_status.sql` after creating/upgrading the Prisma schema. Its PostgreSQL triggers advance `statusRevision` for **every actual status change**, including existing mobile, shop-admin and legacy webhook writers. Same-status writes leave the revision unchanged. Prisma schema push alone does not install triggers. Rolling application code back leaves the additive columns, triggers and receipt table intact; dropping receipts would destroy retry guarantees.

CRM creates one immutable pending command per deal in the staff mutation transaction and retains its canonical stage until the shop acknowledges it. Fenced leases, bounded HTTP and durable exponential backoff survive timeouts/crashes. A conflict is recorded, never automatically rebased. The scheduler polls canonical state every minute and projects explicit per-kind stage IDs only when no pending intent exists. Projection never creates a command, so customer cancellation cannot feed a loop. An optional `commerceOrder` view exposes kind/status/revision/phase/message; the existing timeline records pending/acknowledged/conflicting outcomes.

Direction support is additive: `sunna|semya|osnova|sport`, default `osnova`. Public v1/v2 product collections accept optional `direction`; invalid values return 400. Both query-helper paths and serializers carry the field. `getDirectionCategories(direction)` returns active categories with active matching products.

Catalogue recovery verifies all 119 identities, prices in integer RUB kopecks, 108/11 availability and all 225 asset checksums before mutations. The reviewed `scripts/catalogue-publication.json` contains the source-ID→public-name/direction/safe-format map. Immutable `CatalogueRecovery` receipts preserve raw names/descriptions/categories and image provenance. Imports are create-only under an advisory lock: operator edits, live stock, accepted orders and deleted products survive retries. Changes to a receipt's source require explicit reconciliation. No broad demo seed is part of launch.

Validation: `scripts/test-launch-data.ts` requires the dedicated `hayat_launch_shop_test` database on `hayat-commerce-test-postgres`; it refuses other targets. CRM `commerce-status.e2e.test.ts` uses its registered isolated database. Public production smoke must use explicitly named synthetic fixtures and remove only their recorded IDs.
